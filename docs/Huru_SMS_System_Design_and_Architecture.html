System Design and Architecture

Huru SMS

Multichannel SMS and Web Citizen Information and Guidance System for Tanzania

This document describes how Huru SMS is designed and built: the parts of the system, how they work together, how a question travels from a citizen's phone to an answer, how data is stored, how the system is deployed and secured, and what the citizen and the operator see on screen.

1. Purpose of this document

The Innovation Documentation explains what Huru SMS is and why it was created. This document explains how it is built. It is written for a reader who wants to verify that the submitted source code is a complete, working, original system. It contains:

  • a system overview showing the people and outside services the system talks to (Section 2);
  • the functional design: what each part of the system does (Section 3);
  • the software architecture: layers, components and the source files that implement them (Section 4);
  • the processing flows for an SMS question, a web question and the answer pipeline (Section 5);
  • the data design: database tables and their relationships (Section 6);
  • the deployment and integration design (Section 7) and the security design (Section 8);
  • the technology stack (Section 9) and screenshots of the SMS interface, the web interface and the administration panel (Section 10).

File names in this document (for example app/Services/ConversationService.php) refer to the files reproduced in the Source Code Listing.

2. System overview

Huru SMS is a server application. Citizens reach it in two ways: by sending an SMS starting with the keyword HURU to the shortcode 15054, or by opening the web chat in a browser. Staff of Huru Digital manage the content and settings through a protected administration panel. The application uses three outside services: the SMS gateway that carries messages to and from the mobile networks, a language model service that words the final reply, and a public directory of legal aid providers that is imported periodically.

Figure 1. System context: the people and outside services connected to Huru SMS.
Actor or serviceRole in the system
Citizen (SMS)Sends questions and service commands by SMS from any phone. Identified only by phone number.
Citizen (web)Logs into the web chat with a phone number confirmed by a one-time SMS code. Can search history, rate answers, set name, language and region, and take part in the community board.
OperatorSigns in to the administration panel with e-mail and password. Maintains knowledge entries, the national directory, local services, personas (prompt templates) and system settings; reviews conversations and engine logs; blocks abusive users.
SMS gatewayAfrica's Talking delivers inbound SMS to the webhook and sends outbound replies. Any gateway with a similar HTTP interface can replace it; the integration is isolated in one class.
Language model serviceReceives the system instructions and conversation turns assembled by Huru SMS and returns the worded reply. It never receives the citizen's name or number. The provider is behind an interface and can be swapped.
DatabaseStores citizens, messages, engine logs, feedback, knowledge, directories, templates, settings, community content, sessions, cache and the job queue.

3.2 Service commands (both channels)

CommandEffect
MSAADA, HELP, MENU, ?Short guide to the service in the citizen's language
ACHA, STOP, SITAKI, ONDOAOpt out: no further replies by SMS until the citizen sends a start command
ANZA, START, RUDIResume the service
LUGHA SW / LUGHA EN / LUGHA AUTOFix the reply language to Kiswahili or English, or follow the language written
JINA <name>Save the citizen's name for a personal reply
MKOA <region or district>Save the citizen's region (recognises all 31 regions and common districts) so nearby services are prioritised

Commands are answered directly by the application and never reach the language model.

4. Software architecture

The application follows a layered architecture on the Laravel framework. Each layer only calls the layer below it. Both channels enter the same conversation engine, so the behaviour never differs between SMS and web.

Figure 2. Layered architecture. Every box is an original class or view in the source code listing.

4.1 Design principles

  • One engine, many channels. SMS and web both call ConversationService::handle(). Channel-specific limits (for example the 120-word SMS budget) are passed as context, not duplicated.
  • Context before generation. The application decides the topic, language, location, knowledge, nearby services and official contacts before the language model is called. The model only words a reply inside those instructions, which keeps answers Tanzanian and prevents invented numbers or offices.
  • Replaceable providers. The model is used through the LlmClient interface and the gateway through SmsService; either can be swapped without touching the engine.
  • Operator control without code changes. Knowledge, directories, personas and settings live in the database and are edited in the admin panel. Settings are whitelisted in Support/Settings.php so only known keys with validated types can be changed.
  • Graceful degradation. If the model, the gateway or the key is unavailable the citizen gets a polite message, the failure is logged with its cause, and commands keep working.

Component (file)Responsibility

6. Data design

The database has 14 application tables plus the framework tables for sessions, cache and the job queue. Figure 6 shows the application tables and their relationships; the tables that follow describe the important columns.

Figure 6. Entity-relationship diagram of the application tables (migrations in database/migrations/).
TablePurpose and notable design choices
usersOne row per citizen or operator. Citizens are identified by phone number in +255 format; operators by e-mail and password with role = admin. Holds the hashed one-time code, strike count, ban and opt-out flags, and preferences.
messagesEvery inbound and outbound text on both channels, with language and topic. Indexed by citizen and time, and by channel and time, for history search and dashboard statistics.
ai_logsOne row per engine call attached to the outbound message: the full instructions sent, the raw response, status, token counts and latency. Lets the operator audit why an answer was given.
feedbackHelpful / not helpful rating per answer per citizen (unique pair).
knowledge_entriesVerified facts the engine quotes; bilingual with keywords for retrieval; can be switched off without deleting.
prompt_templatesPersonas: the tone and rules per topic and language, editable by the operator.
reference_contactsNational institutions and hotlines with a verification date and an emergency flag, so emergency numbers are listed first.
local_resourcesServices by region, district and ward (186 legal aid providers imported, plus operator entries). Indexed by region and district for nearby lookups.
system_settingsKey-value store; only keys defined in the settings schema are accepted and values are validated and cached.
community_*Threads, membership, posts with replies, reactions and invitations for the community board.
sessions, cache, jobsLaravel framework tables: web sessions, cached settings and rate limits, and the queue of SMS messages waiting to be processed.

7. Deployment and integration design

Figure 7. Deployment view. Outbound calls (blue) use verified TLS; the gateway callback is protected by a secret token.

7.1 Integration details

IntegrationHow it is implemented
Inbound SMSThe gateway posts from, to, text, id to /api/sms/inbound. The VerifySmsWebhook middleware compares the token query parameter or X-Webhook-Token header with the configured secret. With AT_REQUIRE_KEYWORD on, messages without the keyword are ignored (shared shortcodes). The keyword is removed and the message queued.
Outbound SMSSmsService posts to the gateway messaging endpoint (sandbox or live chosen by the username) with the shortcode as sender. Long replies are kept within the SMS word budget by the engine.
Language modelGeminiClient calls generateContent with a system instruction and the conversation turns; model name, temperature and maximum tokens come from settings. Responses are classified as ok, safety-blocked, error or unconfigured.
TLSAll outbound HTTPS calls verify certificates using a bundled CA store, so the application behaves the same on Windows and Linux hosts.
Legal aid registerThe console command huru:import-legal-aid downloads the public provider list, maps names, regions, districts and addresses to local_resources, and runs weekly from the scheduler.
Offline web useA service worker caches the application shell and shows an offline page with the SMS instructions; chat, admin and API responses are never cached.

8. Security and privacy design

ConcernDesign
Citizen login (web)Phone number plus one-time SMS code; the code is stored hashed, expires after a set number of minutes, allows five attempts, and requests are rate-limited per number. The session is regenerated and the CSRF token rotated after login.
Operator loginE-mail and hashed password; login attempts throttled; every admin route requires an authenticated user with the admin role (EnsureAdmin).
Gateway callbackSecret token required on every inbound SMS and delivery report; requests without it are rejected before any processing.
Request protectionCSRF tokens on all state-changing web requests; per-route throttling on OTP, sending, posting and login; input validation on every controller.
Abuse and safetyWord-list moderation with warnings, strikes and bans; model safety blocks count as strikes; emergencies surface official hotlines first; per-citizen rate limit.
Data minimisationOnly the phone number and the conversation are stored. The name and number are never sent to the model. Phone numbers are masked in the admin panel and in logs.
SecretsAPI keys, the webhook secret and database credentials live only in the .env file, which is excluded from the deposited package and from version control.
Settings integrityOnly keys declared in the settings schema can be written; each value is validated against its declared type and options.
TransportHTTPS for citizens and operators; verified TLS for all outbound calls.
